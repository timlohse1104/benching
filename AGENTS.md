# AGENTS.md

Guidance for AI coding agents (OpenCode, Claude Code, etc.) working in this repo.

## What this project is

A local-first LLM test bench. The user authors prompts as `.txt` files and a YAML list of models; the bench fans out the prompt × model matrix, saves one self-contained HTML per cell, validates each HTML two ways, and renders a static dashboard.

Local models (Ollama, LM Studio, llama.cpp, vLLM) are first-class and need no API key. Cloud is optional via `.env`.

## Repo layout

```
config/models.yaml              # model registry
prompts/*.txt                   # one prompt per file; filename stem = prompt id
src/llm_check/
  cli.py                        # argparse entry: run / validate / list
  config.py                     # YAML + .env loading, model classification
  providers.py                  # litellm wrapper + dry-run canned provider
  validators.py                 # html5lib parser pass + Playwright headless pass
  runner.py                     # asyncio orchestration + preflight + results.json
  reporter.py                   # injects results.json into dashboard template
  dashboard/                    # index.html.tmpl, app.js, styles.css (vanilla)
runs/                           # output, gitignored
```

## Conventions

- Output filename for each cell: `{prompt_id}__{model_id}.html` (double underscore).
- Each model produces its own run directory: `runs/{timestamp}__{model_id}/`. There is no multi-model run directory. The top-level `runs/index.html` is an aggregate generated by `reporter.render_root_dashboard`, which scans `runs/*/results.json` and includes every run (newest first, rows grouped by model label). Because the same `model_id` can appear in several runs, the aggregate payload keys models/cells by `uid` / `model_uid` = `{run_dir}::{model_id}`; per-model dashboards have no `uid` and the JS falls back to the plain `id`.
- All file paths inside a per-model `results.json` are stored relative to that run directory (e.g. `outputs/foo.html`, `thumbnails/foo.png`). The aggregator prefixes them with the run-dir name when stitching the combined payload, so the dashboard JS can use `cell.html_file` and `cell.thumbnail` verbatim as URLs.
- Status values are exactly: `ok | warnings | broken | failed`. Do not invent new ones without also updating the dashboard CSS (`badge-*`) and `app.js`.
- The dashboard runs from `file://` and must not depend on a server. Everything it needs lives in `runs/<timestamp>/` (data embedded into `index.html`).
- The dry-run provider (`dryrun/*`) is the only provider that never touches the network. Keep it that way - it is what makes the bench testable in CI.
- Concurrency: respect the global `defaults.concurrency`, per-model `concurrency`, and a per-endpoint semaphore that serializes all cells targeting the same `api_base` (one llama.cpp server can only serve its loaded model). Local single-GPU models default to 1.
- llama.cpp / OpenAI-compatible local servers: the wire model name is what `GET {api_base}/v1/models` returns, set via `model_name` in YAML. The preflight probes that endpoint, prints served names, and skips entries whose `model_name` is not currently served.
- Per-model `kind` (YAML, optional): free-form label normalized by `_clean_kind` in `config.py` (str, stripped, max 20 chars). Cosmetic only — rendered as a badge in the per-run and aggregate dashboards; does not affect local/cloud classification. Not to be confused with `ValidationIssue.kind`.

## Common tasks

### Add a new validator check
Edit `src/llm_check/validators.py`. Append `ValidationIssue` entries to `parse_issues` (static) or `runtime_issues` (dynamic). Use one of the existing `kind` strings or add a new one and surface it in the Errors tab grouping naturally (`kind` is shown verbatim).

### Add a new LLM provider
You probably do not need to write code. `litellm` already supports it - just add a YAML entry with the right `provider` string and (if local) `api_base`. If a new env var name is involved, add it to `PROVIDER_ENV_VAR` in `config.py` so the preflight check can detect a missing key.

### Add a dashboard view
Add a tab button + `<section class="tab-panel">` in `dashboard/index.html.tmpl`, render in `app.js` from `window.RESULTS`, style in `styles.css`. Keep it vanilla; no build step.

### Add a CLI flag
`src/llm_check/cli.py`. Flags that affect a run should also be persisted into `results.json` (see `_build_payload` in `runner.py`) so re-rendering via `llm-check validate` produces the same dashboard.

## Testing without LLMs

`llm-check run --dry-run` is the canonical smoke test. It exercises:

- config + prompt loading
- async orchestration and semaphores
- HTML extraction (the canned set deliberately includes broken cases)
- both validator passes
- thumbnail capture (requires `playwright install chromium`)
- results.json round trip
- dashboard rendering

If a change does not break dry-run, it almost certainly works for real providers too.

## Things to avoid

- Do not commit `runs/` or `.env`.
- Do not pull a JS framework or bundler into the dashboard.
- Do not bypass `litellm` for cloud providers - it normalizes errors and cost.
- Do not add network calls to the dry-run path.
- Do not crash a run because one model is unreachable; surface it in the preflight table and continue with the rest.
